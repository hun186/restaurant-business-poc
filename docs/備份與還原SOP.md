# 餐廳好管家｜自動備份與停機還原 SOP（PoC）

> 僅適用固定主機的 Node.js + SQLite 本機模式。公開 Vercel 展示站不連真實資料庫，**不提供可還原的營運備份**。

## 業主如何管理備份

登入本機 `http://127.0.0.1:3000` 的**業主帳號** →「系統管理 → 備份管理」：

- **自動備份間隔**：預設每 1 天檢查一次（可設 1–365 天）。**自動備份保留份數**：預設 50 份（可設 1–500 份）。設定保存在 `backup_settings` SQLite 表中。
- 系統開始執行後會立即檢查是否到期，之後每分鐘檢查。若服務或電腦停止，不會自行執行；重新啟動後逾期只補做一次檢查。
- 自動備份會掃描持久資料（營運表、使用者、重要稽核記錄），不計入自動備份設定、暫時性 Session、登入嘗試表；若與上一份**仍存在且經驗證有效的自動備份**內容一致，就記錄「無變更跳過」及下次日期，不再新增相同 SQLite 檔。沒有上次有效版本時不可跳過。
- 「立即建立手動備份」**每次**建立新的完整快照，不會因無變更而跳過。手動與升級前的 `migration` 版本不受自動清理影響，只能由業主手動刪除。
- 「下載」匯出 SQLite 副本至本機，由業主管理；「刪除」須再次確認，刪除後無法恢復。

## 實作與錯誤防護

- `src/backup-worker.js` 背景 Worker 執行 `src/backup-manager.js`，網站主執行緒仍能回應。建立檔案採 `VACUUM INTO *.partial` → SQLite `quick_check`、`foreign_key_check`、schema 結構檢驗 → 改名為 `restaurant-backup-YYYYMMDD-HHMMSS-xxxxxxxx-(auto|manual).sqlite`。
- 先以專用 `.restaurant-backup.lock` 確保不會兩個程序同時建立同一組備份；只有確認建立者程序已消失且超過 2 小時才回收鎖。超過 24 小時的符合管理規則 `.partial` 可在持鎖下清理；**絕不將暫存檔當成已完成備份**。
- 自動備份成功並驗證後才輪替較舊的自動版本；若清理舊檔失敗，新版本應保留，錯誤會留在管理頁。失敗不會用空庫替代舊資料。
- 下載／刪除皆驗證預定格式、拒絕 `../` 與符號連結；HTTP API 僅允許登入業主操作，異動採 Session、CSRF、防跨站來源檢查，動作寫入稽核。
- Windows 備份目錄與檔案使用 NTFS ACL：只允許目前 SID、SYSTEM 與 Administrators；驗證失敗即拒絕備份操作。非 Windows 使用 0700 目錄、0600 檔案權限。
- SQLite `user_version=1` 升級到 v2 前會先建立驗證成功的 `migration` 快照，再於交易內新增 `backup_settings`；v2 既有表若缺失，不會自行補建空表。

## 重要限制

- 這是**同一台主機的本機備份**，不抵抗整台電腦毀損、勒索軟體或備份裝置失竊；請定期將下載的備份再複製到另一個受保護磁碟。異地複製、Windows 實機還原及災難演練尚需驗證。
- 若更新至新版時原 DB 已遺失或完整性不良，程式會拒絕建立空庫；應停止操作、保留現場檔案並連絡維運者。
- 備份檔包含員工／營運／帳號雜湊等敏感資訊；**不可傳到公開 GitHub、Vercel 示範站、未授權檔案分享空間**。

## 停機還原步驟（需要有技術人員）

1. **停止網站及備份 Worker**（等待正在執行的備份結束），先完整封存 `data/restaurant.sqlite` 與若存在的 `data/restaurant.sqlite-wal`、`data/restaurant.sqlite-shm` 三者，以及其他現場相關設定，作為復原前證據。
2. 選擇需要的已驗證備份；先在**隔離測試資料夾**使用 SQLite `PRAGMA quick_check`、`PRAGMA foreign_key_check` 確認完整，並檢視正確日期與資料版本。若是 `migration`（v1），需要再經版本遷移。
3. 將正式資料庫及舊 WAL/SHM **整組移出**正式 `data/`，確保沒有遺留舊 WAL/SHM。**不得只在原路徑覆寫 `.sqlite`，更不能在服務運作中還原。**
4. 在**服務未啟動的隔離工作副本**先完成下方「復原前舊 Session 失效」檢查；確認 `sessions` 為 0 後才將該副本放回正式 `data/restaurant.sqlite`。**不可直接啟動尚含舊 Session 的快照。** 檢查檔案／目錄 ACL、`.installed` 標記與 OS 存取權限，確認無舊 WAL/SHM 後才啟動程式。
5. 以**重新登入**的測試帳號核對筆數、重要庫存記錄與日期，驗證舊 Cookie 無效、授權及功能，再交還業主。還原演練與簽收尚未完成，不能因此文件宣稱已正式驗收。

## 異常 SOP

| 現象 | 建議處置 |
| --- | --- |
| `E_DB` | 停止操作；可能資料庫不存在、已損毀或升級前資料有缺失。不要刪 `.installed` 或清除 WAL/SHM 嘗試重建。 |
| `E_BACKUP_BUSY` | 有其他備份作業或未安全過期的鎖；先確認主機進程與備份記錄，不要強制刪鎖。 |
| `E_BACKUP` | 檢查磁碟容量、專用備份資料夾是否有符號連結、NTFS ACL、目錄寫入權限及失敗訊息。 |
| 排程沒執行 | 確認網站 Node.js 程序持續執行、上次檢查時間及備份間隔；關機後會在下次啟動補檢。 |
| `無變更跳過` | 正常行為；備份未新增但上次有效備份仍須存在。若想另外存留手動快照可按「立即建立手動備份」。 |

## 外接磁碟與獨立電腦上的備份唯讀驗證（RB-011）

這一段只驗證「備份搬到沒有原來 data/ 資料庫的電腦仍能讀取」，**不是啟動還原或災難復原簽收**。

1. 原主機用「備份資料.bat」建立手動快照，再用「備份還原演練.bat」取得**該份**備份 SHA-256。把完整 64 碼、日期、檔名與來源主機代號存於獨立私有紀錄。
2. 使用業主核准、已加密且受實體管制的媒體，將 .sqlite 複製至另一台 Windows 電腦。**SHA-256 必須取自原主機的獨立紀錄，不得用搬運後檔案現算的值冒充預期值。**
3. 第二台 Windows 主機只需完整餐廳好管家程式與 Node.js 22.13+，**不需要原 data/ 資料庫**。雙擊「異機備份驗證.bat」，依畫面輸入外接 .sqlite 完整路徑與原主機的 SHA-256。進階用法：`node tools/offsite-backup-verify.js --file "E:\Backup\restaurant-backup-YYYYMMDD-HHMMSS-xxxxxxxx-manual.sqlite" --sha256 <原始 SHA-256>`。
4. 工具僅從來源檔案描述符讀取、在受保護的暫存目錄複製並比對 SHA-256，然後只在隔離副本進行 SQLite Schema/quick_check/FK/指紋與有效業主/筆數驗證，最後清理隔離副本。**不修改外接檔案 ACL、不在來源產生 WAL/SHM、不建立正式 data/ 或啟動服務**。

判讀：`E_CONFIG`＝參數/雜湊格式錯誤；`E_BACKUP`＝備份不存在或並非安全的一般檔案；`E_DIGEST`＝搬運後檔案和原主機雜湊不同；`E_VERIFY` 或 `E_DB`＝隔離複製或 SQLite 檢驗失敗。失敗應停止，**不得為了通過驗證而覆寫來源備份或原主機資料庫**。

PASS 僅能證明外接備份的位元組與來源紀錄一致、可被此版本的 SQLite 檢驗。後續仍必須由技術人員在獨立隔離 Windows 電腦做真正停機還原、啟動與登入／權限檢查，驗證跨磁碟加密/異地備份及 RTO/RPO，最後由業主簽收。

敏感資料不應被傳到 GitHub、公開 Vercel、Cloudflare Preview 或對話附件；如需提供報告，只使用去識別機器代號、Hash、測試結果與錯誤代碼。

## 合成資料復原後啟動驗證（RB-011-SMOKE，自動化測試）

`npm run check` 的 `tests/recovered-service-smoke.test.js` 僅使用新建的**虛構測試資料**，在同一個 CI 執行環境的另一個隔離資料目錄模擬「從備份還原→以現有 SQLite 啟動 Node HTTP 服務→業主／主管登入→讀取食材與概況→跨角色限制 403」。備份來源不修改；毀損復原副本必須拒絕開啟。此測試比單純檔案 SHA-256 更接近應用程式啟動，但**不是**真正的第二台 Windows 主機、實體磁碟故障、遠端使用者登入或營運資料復原驗收。

**正式還原時的重要安全補充：** 舊快照可能包含仍未過期、甚至在備份之後已遭撤銷的 `sessions` 紀錄；復原時若直接啟動服務，歷史 Cookie 可能被重新接受。技術人員應先在**已驗證的復原工作副本**、**正式服務啟動前**以受控離線 SQLite 交易清空 `sessions`，確認沒有有效舊 Session，要求所有人重新登入；不得清理、改寫原始備份或原主機。須封存原 DB/WAL/SHM 以供鑑識／回滾，完整確認權限、登入、業務紀錄與 RTO/RPO 後才可業主簽收。本階段不提供自動寫入式正式還原工具，也不宣稱舊 Session 已在現場成功撤銷。

## 復原前舊 Session 失效：離線工作副本檢查（RB-011-SESSION）

舊備份內 `sessions` 有可能仍保留有效的 `token_hash`；若在災難前該憑證已被登出、停權或外洩，直接啟動舊快照可能把原本失效的 Cookie **復活**。`tests/restore-session-revocation.test.js` 已在虛構資料中證明：未清理的隔離副本可接受舊 Cookie；對**另一份**隔離副本於停機狀態清空 Session 後，舊 Cookie 回 401，既有帳號重新輸入密碼登入仍可使用，原始備份及庫存資料不受更動。

**現場程序（限具備 SQLite/Windows 權限與停機能力的技術人員）：**

1. 先停掉 Node 服務與備份 Worker；對原主機的 `restaurant.sqlite`、`-wal`、`-shm` 完整封存，分別記錄來源備份檔與 SHA-256。對來源備份只做唯讀驗證，**不要以 SQLite 寫入開啟原始備份**。
2. 在受管制的**獨立、已保護權限**的還原工作目錄，建立備份的全新可寫副本（檔名可使用 `restaurant.sqlite`）。核對副本 SHA-256 等於原備份的獨立雜湊紀錄，SQLite `quick_check`、`foreign_key_check`、Schema 版本與必要業主/營運資料均正常。若其中任一失敗，立即停止；不可「修補」來源備份。
3. 保持服務完全停止，**只對該已驗證的隔離工作副本**開啟 SQLite 管理工具，在單一交易執行下列 SQL；若交易失敗，回滾，不進行上線：

   ```sql
   BEGIN IMMEDIATE;
   DELETE FROM sessions;
   COMMIT;
   SELECT COUNT(*) AS remaining_sessions FROM sessions;
   ```

   `remaining_sessions` 必須為 **0**，並再次驗證 SQLite `quick_check`、`foreign_key_check` 及主要營運資料一致。此交易刻意不更動 `users` 密碼雜湊、門市授權、稽核或 `stock_moves`。SQLite GUI/CLI 操作、NTFS ACL、舊 WAL/SHM 分離以及正式 DB 替換，均需由授權技術人員在現場辦理；專案**尚未提供一鍵覆寫正式資料庫**的工具。
4. 將清理完且已驗證的副本移至正式資料目錄（不得留下舊 WAL/SHM），再次確認權限和離線備份已封存後啟動服務。驗證**舊 Cookie `/api/me` 回 401**、Owner/Manager 重新登入、門市權限與庫存等營運資料正確，核對異地備份/RTO/RPO 並簽收。

**驗收邊界：** 本輪僅把舊 Session 復活風險納入合成快照的 CI 回歸測試；仍沒有在真實業主 Windows 主機執行上列交易、跨機器還原、外接磁碟故障演練或實站 RTO/RPO 計時。不得將 GitHub CI 通過描述成正式還原／資安／業主簽收完成。
